# Build Template Notes

This is a **source template**, not a claimed completed simulation. It was prepared against the public Veins 5.3.1 application API but could not be compiled in the current environment because OMNeT++, SUMO, and Veins are not installed here.

## What the template does

- `PQVehicleApp` keeps Veins' standard periodic BSM generation and counts BSMs generated while the sender is within the paper's 150 m RSU radius.
- `PQRSUApp` records application-level receive latency for BSMs whose sender position was within the 150 m radius at send time.
- The latency uses OMNeT++ message creation time, which is preserved for cloned messages, making it appropriate for end-to-end packet timing at this layer.
- `beaconLengthBits` is set to the paper's serialized authentication tuple size; lower layers then add their own protocol overhead.

## Why custom coverage counters are included

Using `generatedBSMs` from every vehicle in the whole StudyArea would give the wrong PDR denominator for one RSU. `generatedInRsuCoverage` provides the denominator for messages generated by vehicles inside the stated coverage disk; `receivedFromRsuCoverage` is the corresponding RSU numerator.

## Before scientific use

1. Place these files in an OMNeT++ project that references Veins 5.3.1.
2. Copy the Veins example `config.xml` and `antenna.xml` or replace them with a documented PHY model.
3. Copy the StudyArea `.net.xml` and route file from the paper artifact.
4. Make a SUMO 1.22-compatible `studyarea_veins.sumocfg` and preserve it with the results.
5. Compile. Resolve any API/build differences **before** running the experimental matrix.
6. Validate one tiny scenario manually: one sender, one RSU, very low load. PDR should be near 1 and measured latency nonnegative.
7. Only then execute the scout/confirmatory matrices.

## Rendering a concrete omnetpp.ini

Use `../scripts/render_veins_ini.py`, for example:

```bash
python3 ../scripts/render_veins_ini.py \
  --template omnetpp.ini.template --out omnetpp.ini \
  --mode digest --phy 12 --msg-rate 10 --seed 1 --sim-time 120 --run-tag digest_12M_10Hz_s1
```

The renderer maps:

- full -> 10,662 B
- digest -> 3,465 B
- 10 Hz -> 0.1 s beacon interval
- 20 Hz -> 0.05 s beacon interval
